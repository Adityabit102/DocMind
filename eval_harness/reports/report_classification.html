On clean images the layout-aware engine underperforms the raw-OCR baseline: field accuracy 0.99 → 0.89 (-0.10). The degradation charts show where the gap widens under blur/skew/low-resolution — the actual point of the 'OCR enhancement' claim.

At max severity the layout-aware engine is more robust on: pixel_noise (0.00→0.31). This is the accuracy/robustness trade-off the degradation curves exist to expose — a single clean number would have hidden it.

Donut VLM (real run): field accuracy 0.00. This is a genuine, unflattering result — reported as-is. Donut here is donut-base-finetuned-cord-v2, fine-tuned on the CORD receipt schema, so it emits receipt tags rather than this form’s keys, e.g.:
<s_menu><s_nm> INVOICE</s_nm><s_discountprice> -52445</s_discountprice><s_price> 2026-03-13</s_price> … <s_total_price> $8829.12</s_total_price>
The OCR content is clearly captured (invoice number, date, total all appear), but under CORD field names — so mapping to the Invoice No / Vendor / Bill To schema fails almost everywhere. This is a schema-mismatch failure, not an OCR failure: an off-the-shelf VLM fine-tuned for a different document type does not transfer zero-shot to a new field schema. Closing this gap would require fine-tuning Donut on this schema (out of scope for a CPU box) — noted honestly rather than hidden.
